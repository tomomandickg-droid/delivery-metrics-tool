# Delivery Metrics Tool — Technical Plan (v1)

Status: **approved on 27 Nov 2026**. All open questions are decided, including the sample date shift (§8.2) and the skip rules for impossible date order and duplicate keys (§4.3). See the delivery notes in `spec.md`.

---

## 1. Approach in one paragraph

A single-page web app that runs entirely in the browser. The user drops a Jira CSV export onto the page (or clicks "Load sample data"). The file is parsed and checked, and all metrics are calculated locally. The data never leaves the machine, so v1 needs no server, database or accounts. All calculation logic lives in a pure TypeScript `domain/` layer with no UI code. Every domain function receives "today" as a parameter instead of reading the clock, so tests and manual checks always use a fixed date. The React UI only displays what the domain layer returns.

How to run it locally: `npm install`, then `npm run dev`, then open the printed localhost URL.

## 4. Data handling

### 4.1 Dates and inclusive day counting

- Every date is reduced to a **calendar date** (year, month, day) as written in the CSV. Any time of day is dropped. No time zone conversion is done.
- A calendar date is stored as a **day number** (days since 1970-01-01, computed with `Date.UTC(y, m-1, d) / 86_400_000`). UTC is used only for this arithmetic, so daylight-saving changes can never move a date.
- **Inclusive day count**:

  ```
  inclusiveDays(start, end) = dayNumber(end) - dayNumber(start) + 1
  ```

  Unit test cases:
  - 1 Nov → 1 Nov = **1 day**; 1 Nov → 6 Nov = **6 days** (the spec's examples)
  - 31 Oct 23:59 → 1 Nov 00:01 = **2 days** (time of day ignored)
  - 28 Feb 2028 → 1 Mar 2028 = **3 days** (leap year)
  - 24 Oct → 26 Oct 2026, across the end of daylight saving time = **3 days**

- The minimum duration is 1 day. A 0-day value cannot occur.

**Supported formats** (decided). Each may be followed by a time of day, which is ignored:

| Format              | Example                          | Rule                                                                |
| ------------------- | -------------------------------- | ------------------------------------------------------------------- |
| Jira default export | `27/Nov/26 10:15 AM`             | `dd/MMM/yy`, English month abbreviation (any case), `yy` → `20yy`   |
| ISO                 | `2026-11-27`, `2026-11-27T10:15` | `YYYY-MM-DD`; the date part is used as written                      |
| Day.month.year      | `27.11.2026`, `27.11.2026.`      | `DD.MM.YYYY`; a trailing dot (as in Croatian date style) is allowed |

The three formats use different separators (`/`, `-`, `.`), so a value can never match two of them. Dates that don't exist, such as `31.02.2026` or `30/Feb/26`, are invalid.

### 4.2 Column validation

Required columns: `Issue key`, `Issue Type`, `Status`, `Created`, `Resolved`, `Started`.

- Headers are matched after trimming spaces, ignoring upper/lower case and removing a leading byte-order mark (BOM).
- `Started` also matches `Custom field (Started)`, which is the name Jira gives a custom field in CSV exports.
- If a header appears more than once, the first one is used.
- **Every** missing column is named in one error, e.g. `Missing required columns: "Resolved", "Started"`. When any column is missing, no metrics are shown.
- File-level errors with a clear message: the file is empty, has a header but no data rows, or is not valid CSV.

### 4.3 Turning rows into issues; skipped rows

`Issue = { key, type, status, created, resolved?, started? }`. The three dates are `CalendarDate` values.

A row is **skipped** (decision 7) when any of these is true. Each skipped row is recorded with its issue key and the reason:

| Reason                                       | Example                                               |
| -------------------------------------------- | ----------------------------------------------------- |
| `Created` is empty or not a valid date       | `Created = "soon"`                                    |
| `Resolved` is not empty and not a valid date | `Resolved = "31.02.2026"`                             |
| `Started` is not empty and not a valid date  | `Started = "2026-13-01"`                              |
| `Resolved` is earlier than `Created`         | the dates are each valid, but the order is impossible |
| `Started` is later than `Resolved`           | the dates are each valid, but the order is impossible |
| Duplicate `Issue key`                        | the first row is kept; later ones are skipped         |

**Not** reasons to skip:

- An empty `Resolved` or `Started`. That is normal: the issue is open, or not started yet.
- `Started` earlier than `Created`. The issue is kept, and cycle time counts from Created (§6.3). `toIssues` also returns these issues in a separate `startedBeforeCreated` list (rule changed 27 Nov 2026).

The dashboard shows "N rows skipped" with the list of keys and reasons (a row with no key is shown as "row 17"). Below it, the dashboard lists adjusted issues, e.g. "Started before Created: 1 issue, cycle time adjusted (MS-7)". Both lists cover the whole file and do not change with the Issue Type filter.

## 5. Reporting window

Decisions 1, 2 and 6. Implemented in `window.ts` as `reportingWindow(today)`.

- Weeks run **Monday to Sunday**. Each week is labelled by its Monday, e.g. "w/c 16 Nov".
- The current week (the one containing `today`) is **not finished** and is excluded.
- The window is the **12 completed weeks** before it: from the Monday 12 weeks before the current week's Monday, to the Sunday just before the current week.
- `today` is the viewer's local date when the app runs. In tests it is always passed in explicitly.

Worked example (becomes a unit test). Today is Friday 27 Nov 2026:

- The current week is Mon 23 Nov – Sun 29 Nov. It is excluded.
- The last completed week is Mon 16 Nov – Sun 22 Nov.
- The window is **Mon 31 Aug 2026 – Sun 22 Nov 2026**, which is 84 days.
- If today were Monday 23 Nov, the window would be the same. If today were Monday 30 Nov, the window would move forward by one week.

An issue is "in the window" when its **Resolved** date falls in the window.

If no issues were resolved in the window, the dashboard says so and shows the latest Resolved date in the file. For example: "No issues resolved between 31 Aug and 22 Nov 2026. The latest Resolved date in this file is 14 Jun 2026." This explains an empty dashboard after an old export is uploaded.

## 6. Metric calculations

All metrics are calculated on the issues that pass the Issue Type filter (§7). **Done = the issue has a Resolved date** (decision 5). The `Status` column is used only to group WIP.

### 6.1 Throughput

- Count the issues resolved in each of the 12 weeks of the window. Weeks with none show 0.
- Chart: 12 bars, oldest first.
- Card: the **average per week** = (issues resolved in the window) ÷ 12, shown with one decimal (decision 3). Weeks with 0 are part of the average.

### 6.2 Lead time

- Included: issues resolved in the window.
- Per issue: `leadTime = inclusiveDays(created, resolved)`.
- Card: median and 85th percentile in days, plus the number of issues (n).

### 6.3 Cycle time

- Included: issues resolved in the window **that have a Started date**.
- Per issue: `cycleTime = inclusiveDays(max(started, created), resolved)`. If Started is before Created, cycle time is counted from Created, so it equals lead time.
- Card: median, 85th percentile and n, plus a note such as "4 resolved issues have no Started date".

### 6.4 Percentiles

Decision 4: the same method as Excel `PERCENTILE.INC` (linear interpolation between closest ranks):

```
sorted ascending: x[0..n-1]
h = (n - 1) * p              // p = 0.5 for the median, 0.85 for the 85th percentile
result = x[floor(h)] + (h - floor(h)) * (x[ceil(h)] - x[floor(h)])
```

- With p = 0.5 this is the ordinary median, the same as Excel `MEDIAN`.
- Values are shown rounded to 1 decimal and kept at full precision internally.
- n = 0 → the card shows "No data".
- Worked example (becomes a unit test): [1, 2, 3, 4, 10] → median **3**, 85th percentile = 4 + 0.4 × 6 = **6.4**.

### 6.5 Work in progress

- WIP = issues with a **Started date and no Resolved date** (decision 5).
- Issues with neither date are backlog. They are not counted.
- WIP does not use the reporting window. It shows the state at the time of the export.
- Card: the total, plus a count for each `Status` value, largest first.

### 6.6 Lead time distribution chart

- Uses the same issues as the lead time card (resolved in the window).
- A histogram with one bar per number of days (1, 2, 3 …). If the longest lead time is over 30 days, days are grouped into 2-, 5- or 7-day bins so there are about 30 bars at most.
- Labelled vertical lines at the median and the 85th percentile.

## 7. Issue Type filter

Decision 8: multi-select.

- A checkbox for each distinct `Issue Type` in the file, sorted alphabetically, with "Select all" and "Clear" shortcuts. All types are selected after upload.
- Any change recalculates all four cards and both charts with `computeDashboard(issues, selectedTypes, today)`. The window does not depend on the filter.
- If no type is selected, every card shows "No data" and a hint to select at least one type.
- Speed: one pass over at most 5,000 issues plus two sorts takes a few milliseconds, so no extra work is needed to keep filtering fast.

## 8. Sample data

### 8.1 Generator

`scripts/generate-sample.ts` (`npm run generate:sample`) writes `public/sample-data/jira-sample.csv`.

- **Deterministic**: a seeded random generator (mulberry32, fixed seed) and a fixed export date of **Friday 27 Nov 2026**. It never reads the clock, so the output is the same byte for byte on every run.
- **Shape**: about 300 issues created over the 20 weeks before the export date. This gives data inside the 12-week window, older resolved issues before it, and some resolved in the current partial week. Both of the last two must be left out of the window, which the tests check.
  - Issue Types: Story (about 55%), Bug (about 30%), Task (about 15%).
  - Statuses: To Do, In Progress, In Review, Done, Closed.
  - Lead and cycle times follow a right-skewed shape, as real delivery data does.
- **Edge cases included on purpose**: issues created and resolved on the same day; resolved issues without a Started date; WIP issues (Started, not resolved); backlog issues (neither date); all three date formats mixed in; and a few rows with invalid dates, which must appear in the skipped-rows list.
- **Format**: Jira's export layout, with extra columns (`Summary`, `Priority`, `Assignee` with made-up names) among the required ones.
- A size argument (`--count 5000`) produces the large file for the local performance check. That file is not committed.

### 8.2 Keeping the sample inside the window (approved)

Decision 1 ties the window to today's date. So the committed sample, which ends on 27 Nov 2026, would fall out of the window after about three months, and the dashboard would show no data.

**Decision**: the **"Load sample data" button** moves every date in the sample forward by a **whole number of weeks**, so the sample's export week lines up with the current week. Because the shift is whole weeks, each date stays on the same weekday, and every lead time, cycle time and weekly count stays the same. The hand-checked numbers therefore stay valid at any date. The shift applies only to the button. A file uploaded by hand, including `jira-sample.csv` itself, always uses its real dates.

### 8.3 Manual verification (acceptance criterion 3)

- `tests/fixtures/manual-small.csv`: about 15 hand-written issues that cover every rule. They include issues inside the window, before it, in the current partial week, without a Started date, WIP, backlog, each skip reason and all three date formats.
- `manual-small.expected.md`: for today = 27 Nov 2026, the hand calculation of each issue's lead time and cycle time, then the weekly counts, the throughput average, the medians and 85th percentiles, the WIP groups and the skipped keys.
- A unit test checks that the code produces exactly these numbers. A second test checks 5 issues from `jira-sample.csv` against values worked out by hand.

## 9. Performance (≤ 2 s for 5,000 issues), checked locally only

Parsing, checking and calculating run in the browser's main thread, and are expected to take well under 300 ms for 5,000 rows.

`npm run test:perf` runs `e2e/performance.local.spec.ts`. It generates a 5,000-issue file, uploads it in Playwright, and requires all four cards to be visible within 2,000 ms. CI does not run this file: the Playwright config excludes `*.local.spec.ts` unless `test:perf` is used. The result is recorded when the acceptance criteria are reviewed (task 24).

## 11. GitHub Actions and the main-branch gate

`.github/workflows/ci.yml`:

- **Runs on**: `push` to any branch, and `pull_request` to `main`.
- **One job, `ci`**, on `ubuntu-latest` with Node from `.nvmrc` and the npm cache:
  1. `npm ci`
  2. `npm run lint`: ESLint and Prettier check
  3. `npm run typecheck`: `tsc --noEmit`
  4. `npm run test:coverage`: unit and component tests; fails below the coverage threshold
  5. `npm run build`
  6. `npx playwright install --with-deps chromium`, then `npm run test:smoke` against `vite preview`
  7. If the job fails, the Playwright report is uploaded as an artifact
- **Blocking merges to main** is a repository setting, not something the workflow can do. After the first green run, the repository owner turns on: "Require a pull request before merging", plus "Require status checks to pass" with `ci` selected. The README will describe the steps.

### 11.1 Publishing on GitHub Pages (added 27 Nov 2026)

- **Link**: https://tomomandickg-droid.github.io/delivery-metrics-tool/
- **Relative paths**: Vite builds with `base: './'`, so every asset path is relative. The same build works locally at `/` and on Pages under `/delivery-metrics-tool/`. "Load sample data" fetches `./sample-data/jira-sample.csv` from the same place.
- **Workflow** (`.github/workflows/pages.yml`): runs on every push to `main`, plus a manual run. It does `npm ci`, the unit tests and the build, then uploads `dist/` with `actions/upload-pages-artifact` and deploys with `actions/deploy-pages`. Main only receives code through pull requests with a green `ci` check, so whatever is deployed has already passed every check.
- **Repository setting**: Pages, with **GitHub Actions** as the source.
- **Privacy**: unchanged. The page is static, and an uploaded CSV is read in the visitor's browser and never sent anywhere.
